# Threat model

Status: initial, Phase 0, with rows added through Step 8. Each row needs a test before its milestone can be marked DONE.

| # | Threat | Treatment | Test (planned) |
|---|---|---|---|
| T1 | Unauthorised party reads a request or offer | Recipient-scoped encryption | Wrong recipient fails to decrypt: `packages/qoreseal-adapter/test/adapter.test.ts` (C1, offline, throwaway keys) |
| T2 | Lender reads another lender's offer | One single-recipient envelope per offer | Lender B cannot open lender A's offer: `packages/qoreseal-adapter/test/adapter.test.ts` (C2, offline, throwaway keys) |
| T3 | Key substitution / fake recipient key | Verify recipient card against the on-chain ML-DSA and KEM keys (registration path exists in source and is not proven live) | Card for a different KEM key is rejected: `packages/qoreseal-adapter/test/cards.test.ts` (offline, throwaway keys, MOCKED registry; the real chain is not called) |
| T4 | Ciphertext tampering or moving an envelope between deals | QoreSeal AEAD plus project-defined AAD binding request, offer, parties, version (ADR-0007) | Wrong AAD and flipped bytes fail: `packages/qoreseal-adapter/test/adapter.test.ts` and `test/signed-envelope.test.ts` (C3, offline, throwaway keys); frozen bytes in `fixtures/aad-vectors.json` |
| T5 | Forged sender | Hybrid message signature over the envelope hash, post-quantum part required, checked against the on-chain key (ADR-0003) | Classical-only and wrong-key signatures rejected: `packages/qoreseal-adapter/test/signed-envelope.test.ts` (offline, throwaway keys, MOCK account client) |
| T6 | A recipient of a multi-recipient envelope forges a variant for other recipients (QoreSeal spec) | Borrower signs the request; lenders verify the signature and hash | Altered request fails verification: `packages/qoreseal-adapter/test/signed-envelope.test.ts` (offline, throwaway keys, MOCK account client) |
| T7 | App trusts classical-only fields in a signature response | Verifier ignores top-level `pub_key` and `signature`; requires `pq` | Response with `pq` removed is rejected: `packages/qoreseal-adapter/test/signed-envelope.test.ts` and `packages/chain-client/test/verify-hybrid-message.test.ts` |
| T8 | Server compromise | Server holds ciphertext and metadata only. No server exists yet; the diagnostics app writes nothing to browser storage and sends no transaction | `apps/web/test/hygiene.test.ts` (MOCK-free static scan: no storage APIs, no transaction methods, no key-like material in `apps/web/src`). C10 remains PENDING until `apps/api` exists and is reviewed |
| T9 | Unauthorised token withdrawal, reentrancy, malicious tokens | State machine, role checks, safe transfers, reentrancy guard, token allowlist | `packages/contracts/test/mock-tokens.test.ts` (reentrant, no-return, false-return, fee-on-transfer, not allowlisted) and `test/lifecycle.test.ts` (wrong callers): local Hardhat network, mock tokens, not deployed |
| T10 | Decimal and amount errors | Amounts are base units; no rate math; no decimal assumption | `packages/contracts/test/lifecycle.test.ts` runs the lifecycle with a 6-decimal and an 18-decimal token; `test/invariants.test.ts` asserts exact outstanding and balances |
| T11 | Replay or duplicate repayment | One loan per commitment, strict state checks, exact outstanding | `packages/contracts/test/lifecycle.test.ts` (duplicate proposal, double fund, double claim, repayment after Repaid) and `test/default.test.ts` |
| T12 | Metadata leakage | Minimise and document; no privacy claims beyond evidence | Limitations list |
| T15 | A lender funds terms that do not match the signed agreement | The UI must recompute the commitment and compare it with `loanId` and `termsOf()` before enabling fund; the contract only commits to the terms it is given and cannot verify a signature or document | C11 in `docs/ACCEPTANCE_MATRIX.md` (PENDING, `apps/web` not built) |
| T16 | A borrower is given no time to claim | `LoanSettlement` requires `claimDeadline >= fundingDeadline + MINIMUM_CLAIM_WINDOW` (3600 seconds, owner-confirmed) | `packages/contracts/test/review.test.ts` (3599 reverts, 3600 succeeds); ADR-0008 decision 9 |
| T17 | Tokens sent directly to the contract are lost | No sweep function exists by design; such tokens are outside every loan's accounting and stay in the contract | `packages/contracts/test/review.test.ts` (donation does not change accounting and cannot be withdrawn) |
| T18 | A blocklisting or fee-changing token breaks settlement | Partly out of scope: `TestUSD` has no blocklist or fee, but the fest fUSD is also allowlisted (ADR-0013) and its controls are unknown | Limitations list; `TestUSD` source reviewed; fUSD behaviour is not verified |
| T19 | `block.timestamp` on Diana has different semantics or skew from this machine | Read-only block-time comparison during Phase 3b; treat deadlines as approximate until confirmed | `evidence/phase-03b-result.md` (read-only sample); ADR-0011 |
| T13 | Lost decryption key | Backup phrase shown once; documented loss of data (ADR-0005) | UX review |
| T14 | Concurrent signing requests rejected by QoreX | Queue requests in one promise queue (`apps/web/src/wallet/signer.ts`); a rejection is returned and never retried | `apps/web/test/signer.test.ts`: two concurrent calls resolve in order and the second does not reach the MOCK provider until the first settles; rejection is called once. The one-at-a-time behaviour is an owner report (source-lock claim 44), not reproduced against QoreX; the queue is defensive |
| T20 | The owner deploys on the wrong chain or from an account they did not intend | The deploy panel re-reads both chain lanes and `eth_accounts` before every send; the account is shown immediately above each button; every button is disabled unless the guard is ready and the previous step is confirmed | `apps/web/test/deploy.test.ts` (MOCK provider: wrong chain blocks before estimate and send); `docs/evidence/phase-06-owner-checklist.md` (owner confirms both chain IDs and the account) |
| T21 | A timeout or a manual second click deploys twice or loses a deployment | One transaction in flight per step; no automatic retry; a missing receipt is shown as UNCONFIRMED - TIMEOUT and does not unlock the next step; after a timeout the step cannot be re-clicked and the owner must check the hash on the explorer | `apps/web/test/deploy.test.ts` (pending receipt, timeout, reverted receipt, and the next-step disabled check) |
| T22 | The deployed code does not match the bytecode that was reviewed | The verifier hashes `eth_getCode` and compares it with the manifest runtime SHA-256; a mismatch is reported explicitly, and a metadata-only difference is named rather than accepted silently | `scripts/verify-deployment.mjs`; `docs/evidence/phase-06-verify.md` (OWNER-SUPPLIED; not run) |
| T23 | A wallet rejection, including an authorization-window message, is hidden or paraphrased | The panel serialises the exact error object (message, code and other own fields) into a raw block and says it was not retried; the checklist stops the run if button 1 is rejected | `apps/web/test/deploy.test.ts` (the exact rejection text and code are preserved, one send only) |
| T24 | The deployment panel handles key material or persists addresses | No key or seed input, no storage API, no raw transaction and no signing method; the addresses exist only on screen and in the copyable block | `apps/web/test/hygiene.test.ts` (static scan; `eth_sendTransaction` pinned to the deploy module and its click handler) |
| T25 | A stale or differently compiled artifact is deployed | `scripts/build-manifest.mjs` refuses the wrong compiler, target or optimizer and records the source commit and dirty flag; the double build must be identical | `scripts/build-manifest.mjs`; `docs/evidence/phase-06-result.md` (double-build hashes) |
| T26 | A credential or key is committed and published with the repository | gitleaks 8.30.1 over the full history in CI; `.gitleaks.toml` keeps the default rules and allowlists only the public QoreSeal vector fixture | `docs/evidence/phase-07-security.md` (local full-history run: no leaks; CI not run remotely) |
| T27 | A dependency licence blocks redistribution under Apache-2.0 | `scripts/check-licences.mjs` fails on an unreviewed label; conditions for MPL-2.0 and CC-BY-4.0 are recorded in the README credits | `docs/evidence/phase-07-licences.md` (164 packages, 7 reviewed labels) |
| T28 | A known vulnerable dependency is shipped without review | `pnpm audit --prod` is run and the result is recorded; one high advisory is accepted with its unused runtime path and a revisit condition | `docs/evidence/phase-07-security.md`; README limitation 31 |
| T29 | The seal mnemonic is exposed by the page, a log, an error, storage or a network call | The mnemonic is generated in the browser, shown once behind an "I have saved it" confirmation, held in memory only and never stored, logged, placed in a URL or sent; the script reads it only from `LOANSHARK_SEAL_MNEMONIC`; keys are private fields with redacted debug/JSON output | `packages/seal-account/test/redaction.test.ts` and `test/browser-safety.test.ts` (static and runtime, TEST ONLY mnemonic); `apps/web/test/hygiene.test.ts` (no storage API, no fetch in the seal panel, mnemonic cleared after confirmation); ADR-0005 |
| T30 | A forged binding statement joins a wallet account W to a seal account E it does not control | Both W and E sign the fixed-line statement; verification requires the post-quantum part of both against the on-chain ML-DSA-87 keys; W's EVM address must equal the `0x` form of W's verified classical key; expiry and chain are checked | `packages/seal-account/test/binding.test.ts` (pq part removed, changed address, expired, wrong account, EVM address mismatch, future timestamp) |
| T31 | A stolen seal key decrypts historical envelopes or a stolen E spends more than its fee balance | Separate E per party; E holds only testnet QOR for fees; envelopes are per-recipient; the card binds the KEM key; the callers label what a compromise of E can and cannot do | `packages/seal-account/test/seal.test.ts` (wrong-recipient refusal); ADR-0004 and ADR-0005 consequences; owner checklist separates the W and E mnemonics |
| T32 | A party reuses the QoreX mnemonic for the seal account, putting the wallet key in the browser | The owner checklist forbids reuse and the browser panel generates a fresh phrase in memory; no code accepts a QoreX seed; `scripts/gen-test-mnemonic.mjs` is TEST ONLY and is forbidden for an owner account | `docs/evidence/phase-08-owner-checklist.md` (OWNER-SUPPLIED confirmation); static check that no source asks for a wallet mnemonic; the generator test only checks word counts and address shape |

Non-goals: anonymity, private ERC-20 transfers, FHE, a private matching engine, credit scoring, legal enforceability, production lending.
