# ADR-0019: Negotiation flow, payload schemas and off-chain state machine

Status: Accepted, 2026-11-26. Local and mock-signer only. No transaction is sent
and no live signature is produced by this repository. The live two-party run is
owner-supplied and PENDING (`docs/evidence/phase-10-owner-checklist.md`).

Context: Step 9 added the encrypted transport (loopback relay, verifying client,
vault, binding flow) and Step 9b added the domain-separated commitment, the local
offer evaluator, the preflight and the privacy footprint. This step joins them
into a borrower and lender flow: create a request, send it, receive and evaluate
an offer, accept it, and have both parties confirm the same agreement. It adds
screens and the relay wiring for public signed confirmations. It does not add
money screens; propose, approve, fund, claim, repay, withdraw, cancel and refund
belong to Step 11.

One borrower and one lender per loan (ADR-0008 decision 1). Each party has a
wallet account W (QoreX) and a seal account E (app-held, ADR-0014).

## Payload schemas

Both payloads are the plaintext of a QoreSeal envelope. They are never sent to
the relay in the clear: the relay stores ciphertext, the AAD context and the
sender signature only.

### `loanshark.request.v1`

| Field | Type | Rule |
|---|---|---|
| `schema` | string | exactly `loanshark.request.v1` |
| `requestId` | string | 16 random bytes, lowercase hex, 32 characters |
| `borrowerW` | string | canonical `qor1` wallet address |
| `lenderW` | string | canonical `qor1` wallet address, different from `borrowerW` |
| `token` | string | `0x` plus 40 hex characters |
| `principal` | string | decimal base units, no sign, no exponent |
| `maxTotalCost` | string | decimal base units, at least `principal` |
| `latestDueDate` | string | decimal unix seconds |
| `note` | string | at most 400 characters, no control characters except LF |
| `createdAt` | string | `YYYY-MM-DDTHH:MM:SSZ` |

### `loanshark.offer.v1`

| Field | Type | Rule |
|---|---|---|
| `schema` | string | exactly `loanshark.offer.v1` |
| `offerId` | string | 16 random bytes, lowercase hex, 32 characters |
| `requestId` | string | the request this answers |
| `borrowerW` | string | canonical `qor1`, equal to the request's borrower |
| `lenderW` | string | canonical `qor1`, equal to the request's lender |
| `terms` | object | exactly the ten `Terms` fields the contract takes |
| `offerExpiresAt` | string | decimal unix seconds |
| `note` | string | at most 400 characters, same control rule |

`terms` carries `borrower`, `lender`, `token` (`0x` addresses), `principal`,
`interest`, `dueDate`, `graceSeconds`, `fundingDeadline`, `claimDeadline`
(decimal strings) and `salt` (32-byte hex). The salts and amounts are strings so
that a JavaScript number cannot round them; `BigInt` is built from the string.
The offer's `terms.principal` is the offered principal and must equal the
request's `principal`; `terms.interest` plus the principal is the total cost.

The salt is generated by the lender with the browser CSPRNG (16 random bytes,
hex-encoded to 32 bytes). ASSUMPTION: a per-offer random salt, not a
counter or a hash of the terms. The alternative, a deterministic salt derived
from the offer id, would let a third party recompute the loan id from public
terms; a random salt keeps the commitment unguessable before it is published.

## Canonical JSON

`canonicalJson(value)` sorts object keys by UTF-16 code unit order, writes no
whitespace, and rejects every number: every integer in these payloads is a
decimal string. Arrays keep their order. The result is UTF-8 encoded for sealing.

ASSUMPTION: strings for every integer and sorted keys, rather than RFC 8785
(JCS). JCS would also sort keys and keep numbers as JSON numbers, but it carries
a normalisation rule for `-0`, exponents and non-finite values that these
payloads do not need, and a number in a payload is exactly the bug this design
wants to make impossible. Two implementations that both sort keys and both forbid
numbers cannot disagree on the bytes.

## Strict validation

Validation rejects unknown fields at every object level (including inside
`terms`), a wrong type, a negative value, a hex or exponent number where a
decimal string is required, a payload over 8 KiB, a note over 400 characters, a
non-canonical `qor1` address (round-trip check), a non-lowercase hex id, and a
`requestId` that does not name the offer's request when both are checked
together. Validation returns a typed failure list; it never throws and never
coerces. A malformed payload is never partially accepted.

## Off-chain state machine

States and the transition that enters each:

| State | Entered by | Meaning |
|---|---|---|
| `Draft` | local form opened | nothing sent |
| `RequestSent` | borrower accepted a request preview | envelope posted to the relay |
| `OfferReceived` | lender opened and verified a request, then sent an offer (borrower side), or borrower saw the offer arrive | encrypted offer exists |
| `OfferEvaluated` | borrower ran `LocalOfferEvaluator` | checks computed, no decision yet |
| `Accepted` | borrower pressed Accept on an eligible offer | borrower confirmation signed |
| `BorrowerConfirmed` | borrower confirmation published and verified | public record exists |
| `LenderConfirmed` | lender confirmation published and verified | both sides confirmed |
| `ReadyToPropose` | both confirmations verified for the same loan id, chain and contract | Step 11 may propose |
| `CounterpartyNotOnboarded` | binding or card missing, invalid or unregistered | nothing is sent |
| `RelayUnavailable` | relay transport, status or schema failure | fail closed |

The reducer is pure. A transition carries the event that caused it and the actor
who may trigger it:

| Transition | Actor |
|---|---|
| `Draft -> RequestSent` | borrower |
| `RequestSent -> OfferReceived` | lender (sends), borrower (receives) |
| `OfferReceived -> OfferEvaluated` | borrower |
| `OfferEvaluated -> Accepted` | borrower, only when `eligible` is true |
| `Accepted -> BorrowerConfirmed` | borrower |
| `BorrowerConfirmed -> LenderConfirmed` | lender |
| `LenderConfirmed -> ReadyToPropose` | either, on the second verified confirmation |
| any -> `CounterpartyNotOnboarded` | either, before sending |
| any -> `RelayUnavailable` | either |

Any other transition is rejected with a typed reason. `CounterpartyNotOnboarded`
and `RelayUnavailable` are terminal for that attempt; the screen offers a retry
that starts a new attempt, it does not silently continue.

## Counterparty identity resolution

A wallet address W is not an encryption address. To send to W an app must find
W's seal account E:

1. `GET /v1/bindings/{W}` through `RelayClient.getBinding`. Both signatures are
   verified against the on-chain ML-DSA-87 keys, the post-quantum part is
   mandatory, and `walletEvmAddress` must be the Ethereum form of W's verified
   classical key (ADR-0014).
2. `GET /v1/cards/{E}` through `RelayClient.getCard`. The card is verified
   against E's registered ML-DSA-87 key and the SHA3-256 of E's registered
   ML-KEM-1024 key.
3. The recipient's ML-KEM-1024 public key is read from
   `/qorechain/pqc/v1/kem/{E}` and used to seal.

If any step is missing, fails verification or times out, the state is
`CounterpartyNotOnboarded` and nothing is sent. A binding or card that fails
verification is shown as REFUSED with its typed reason; it is never shown as
data. The relay itself is not trusted: every record is verified by this client.

## Envelopes

Payload bytes are sealed with QoreSeal in mlkem mode to the recipient's E key
(the on-chain ML-KEM key). The AAD is the ADR-0007 context for the kind, with the
`borrower` and `lender` slots carrying the WALLET (W) `qor1` addresses, per
ADR-0015. The envelope bytes and the context are signed by the sender's E with
the ADR-0003 hybrid message signature, and the relay record carries the
signature, the AAD context and the base64 ciphertext.

Verification on fetch: content address, AAD party fields, then
`verifySignedEnvelope` against E's on-chain ML-DSA-87 key, post-quantum part
mandatory. `RelayClient.getEnvelope` takes an explicit `signerE` because the AAD
names W.

## Agreement confirmation

Both parties compute `canonicalAgreementText(terms)` and the hashes locally,
from the accepted terms. The borrower signs the ADR-0010 v2 confirmation message
(`loanshark/v2/agreement|<evm chain id>|<contract>|<loanId>|<agreementHash>`)
with W through the existing `QorexMessageSigner`; the lender signs the same
message. The message, the two hashes and the domain are recomputed on
verification, and the signature is checked with the post-quantum part required
against W's on-chain key.

The message needs the settlement contract address from a deployment config
file. Until the owner supplies a deployment, the config reports
`"settlement": null`, the confirmation steps show "not deployed" and are
disabled, and no confirmation is signed. The app never hard-codes an address.

Public confirmations are posted to `POST /v1/confirmations` and read from
`GET /v1/confirmations/{loanId}`. The record names the loan id, the EVM chain id,
the verifying contract, the agreement hash, the signer's W address, the role
(`borrower` or `lender`), the raw signature and `createdAt`. The server stores
it content-addressed and immutable, validates the shape and size, refuses
secret-named fields and verifies nothing. The client verifies every signature
before display and refuses a confirmation for another loan id, chain id or
contract.

## Deployment config

A JSON file loaded at runtime by the app (`/deployment.json`):

```json
{
  "format": "loanshark-deployment-config-v1",
  "chainId": 9800,
  "settlement": null,
  "tokens": [
    { "label": "fUSD (fest)", "address": "0x97143B771D34ddb9130b807b135Ae675A5a963CA", "decimals": 6 }
  ]
}
```

`settlement` is `null` or a `0x` address. When it is `null`, the agreement and
confirmation steps are disabled and say "not deployed"; negotiation still works
because it needs no contract. When it is present, the app uses the address and
the token decimals from the file and verifies the chain id against the chain
guard. No address is compiled into the app.

## What is not built in this step

- No money screen: nothing proposes, approves, funds, claims, repays, withdraws,
  cancels or refunds on chain.
- No automated timeout inside a verifier; a hung injected client hangs the
  caller. The screens show a RelayUnavailable state on a rejected fetch.
- No in-app registration of the seal account's keys; the owner-run onboarding
  script does that, and Setup shows the chain registration status read-only.
